# Android release build

The debug APK CI already produces is fine for testing and **cannot go on the
Play Store**: it is signed with Android's universal debug key, which is public.
A release build needs a keystore only you hold.

## What a keystore is, and why nothing here creates one

The keystore is the app's identity. Whoever holds it can publish an update that
Android accepts as genuinely yours, and **it cannot be rotated once the app is
live** — lose it and you cannot update your own app; leak it and someone else
can.

So it is not committed, not generated by any script in this repo, and not
printed by any job. You create it, you keep it, and CI only ever sees it as a
secret it writes to a temporary file.

## 1. Create the keystore (once, on your own machine)

```bash
keytool -genkey -v \
  -keystore gaadiiq-release.jks \
  -alias gaadiiq \
  -keyalg RSA -keysize 2048 -validity 10000
```

It asks for two passwords (store and key — they may be the same) and your
details. `-validity 10000` is ~27 years; Play requires the key to outlive the
app.

**Back it up somewhere you will still have in five years.** A password manager
with file attachments, or an encrypted backup. Not only on the laptop you used.

## 2. Add four GitHub secrets

Settings → Secrets and variables → Actions → New repository secret.

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 gaadiiq-release.jks` — the whole file, one line |
| `ANDROID_KEYSTORE_PASSWORD` | store password from step 1 |
| `ANDROID_KEY_ALIAS` | `gaadiiq` |
| `ANDROID_KEY_PASSWORD` | key password from step 1 |

Base64 because a secret is text. It is not encryption — anyone who can read the
secret can reconstruct the file, which is why only repository admins should be
able to.

## 3. Build a release

The `release-apk` job in `.github/workflows/build-apk.yml` is manual
(`workflow_dispatch`). Actions → Build Android APK → Run workflow → tick
**release**.

It decodes the keystore to a temp file, builds, and deletes it — the file never
reaches the workspace or an artifact.

## How the Gradle side behaves

`android/app/build.gradle` reads four environment variables. If **any** is
missing it defines no signing config, and the release build comes out
**unsigned**.

That is deliberate. The tempting fallback — signing release with the debug key —
produces a file that looks finished, installs happily, and can never be uploaded
to Play. An obviously unsigned artifact is the better failure.

`assembleDebug` is untouched by all of this and keeps working with no setup,
which is what every contributor and the debug job rely on.

## What the release build produces

Two artifacts, in the `gaadiiq-release` run artifact:

| file | for |
|---|---|
| `app-release.aab` | the Play upload. Play has required a bundle for new apps since August 2021 and rejects an APK outright. |
| `app-release.apk` | putting the app on a phone directly — a tester, a demo. Play cannot make you one before the app is listed. |

`versionCode` comes from the workflow **run number**, which only ever
increases, so no submission repeats one. `versionName` is the `version_name`
input on the manual run (default `1.0.0`) — that is the string a user reads,
and it is a decision rather than something derived, because a hotfix sometimes
has to ship ahead of a version already uploaded.

Both default to `1` / `1.0` when the environment variables are absent, so
`assembleDebug` and a local build keep working untouched.

## Before the first Play upload

- **`minifyEnabled false`** — fine to ship, but the artifact is larger than it
  needs to be and the code is not obfuscated.
- **`google-services.json` is absent**, so push notifications are not wired up.
  Gradle logs that and carries on, which means the build passes and the feature
  silently does not exist.
- Play also needs a privacy policy URL, a Data Safety declaration and a content
  rating before a first submission. None of those live in this repo.

## Not verified

The Gradle changes could not be built in the environment they were written in —
the sandbox proxy blocks `dl.google.com`, so no Android dependency resolves and
Gradle cannot run at all. CI's debug job is the check that they did not break
the existing build; **the release path itself has never been executed** and will
not be until someone supplies the four secrets.

That applies to the bundle task and the versionCode wiring as much as to the
signing config: `bundleRelease` is the documented Gradle task and the env-var
read is ordinary Groovy, but neither has been run here. The first manual run
with secrets is the first real test, and the artifact check at the end of the
job is there so a miss shows up as a failure rather than an empty upload.
